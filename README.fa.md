# هوشمندسازی تیکت‌های پشتیبانی مشتری (Customer Support Ticket Intelligence)

*[English version of this page](README.md)*

یک سیستم کامل پردازش زبان طبیعی (NLP) که تیکت‌های ورودی پشتیبانی مشتری را طبقه‌بندی می‌کند، بر اساس منطق بیزینسی یک سطح اولویت به آن‌ها اختصاص می‌دهد، و یک پاسخ پیشنهادی می‌سازد — با ترکیب یک مدل Transformer فاین‌تیون‌شده، تولید پاسخ مبتنی بر RAG، ثبت تیکت‌ها در دیتابیس SQL، و یک داشبورد زنده.

## این سیستم چه کاری انجام می‌دهد؟

برای هر تیکت پشتیبانی ورودی، سیستم:
۱. **نوع درخواست (intent) را تشخیص می‌دهد** — از میان ۲۷ دسته (مانند `cancel_order`، `get_refund`، `payment_issue`) با استفاده از یک مدل DistilBERT فاین‌تیون‌شده.
۲. **اولویت را تعیین می‌کند** — بالا / متوسط / پایین، از طریق یک موتور قانون‌محور شفاف و بیزینسی (نه یک جعبه‌سیاه).
۳. **پیش‌نویس پاسخ می‌سازد** — با بازیابی معنایی (RAG) از پاسخ‌های نمونه‌ی واقعی، که توسط یک مدل زبانی رایگان و کاملاً محلی تولید می‌شود.
۴. **همه‌چیز را ثبت می‌کند** — در یک دیتابیس SQL، به‌همراه کوئری‌های گزارش‌گیری که یک مدیر تیم پشتیبانی واقعاً به آن نیاز دارد.

## امتحانش کنید

- **دمو زنده:** *فعلاً مستقر نشده (Docker روش اصلی برای اجرای بدون هیچ تنظیم اضافه‌ست — پایین‌تر توضیح داده شده).*
- **اجرای محلی با Docker** (روش توصیه‌شده، بدون هیچ تنظیم اضافه‌ای جز خود Docker):
  ```
  git clone https://github.com/amirmovasati/customer-support-ticket-intelligence.git
  cd customer-support-ticket-intelligence
  docker build -t support-ticket-api .
  docker run -p 8000:8000 support-ticket-api
  ```
  سپس آدرس `http://localhost:8000/docs` را برای رابط تعاملی API باز کنید، یا داشبورد را جداگانه اجرا کنید (پایین‌تر توضیح داده شده).

- **اجرای داشبورد به‌صورت محلی:**
  ```
  pip install -r requirements.txt
  streamlit run src/dashboard.py
  ```

## نتایج

| مدل | دقت (Accuracy) | توضیح |
|---|---|---|
| TF-IDF + Logistic Regression (بیسلاین) | ۹۹.۰۳٪ | ساده، سریع، و به‌طرز شگفت‌آوری قوی |
| LSTM (آموزش از صفر) | ۹۸.۱۷٪ | ضعیف‌تر از بیسلاین — نشان‌دهنده‌ی ارزش دانش از‌پیش‌آموخته |
| **DistilBERT فاین‌تیون‌شده** | **۹۹.۷۶٪** | حدود ۷۵٪ کاهش نرخ خطا نسبت به بیسلاین |

دیتاست به‌صورت مصنوعی و با واژگان بسیار متمایز برای هر intent تولید شده، که توضیح‌دهنده‌ی دقت غیرمعمول‌بالای همه‌ی مدل‌هاست — این نکته در فاز تحلیل داده (EDA) بررسی و تأیید شد، نه صرفاً یک فرض.

## معماری

```
متن تیکت
    │
    ▼
[طبقه‌بند intent با DistilBERT]  (فاین‌تیون‌شده، میزبانی‌شده روی Hugging Face Hub)
    │
    ▼
[موتور اولویت‌بندی قانون‌محور]  (intent → اولویت بالا/متوسط/پایین + سیگنال‌های تشدید)
    │
    ▼
[تولید پاسخ با RAG]  (بازیابی با sentence-transformers + تولید با flan-t5)
    │
    ▼
[دیتابیس SQLite]  (با SQLAlchemy — قابل‌ارتقا به PostgreSQL با تغییر یک خط تنظیمات)
    │
    ▼
[بک‌اند FastAPI]  +  [داشبورد Streamlit]
```

## فناوری‌های استفاده‌شده

Python، PyTorch، Hugging Face Transformers & Hub، sentence-transformers، scikit-learn، SQLAlchemy، FastAPI، Streamlit، Docker.

## دیتاست

[دیتاست آموزشی چت‌بات پشتیبانی مشتری Bitext](https://github.com/bitext/customer-support-llm-chatbot-training-dataset) — ۲۶٬۸۷۲ نمونه در ۲۷ intent (پس از حذف موارد تکراری: ۲۴٬۶۳۵ نمونه).

## تصمیمات طراحی مهم

- **رایگان و محلی، به‌صورت عمدی:** تمام مدل‌های استفاده‌شده (DistilBERT، sentence-transformers، flan-t5) متن‌باز، رایگان، و قابل‌اجرا روی CPU هستند — بدون نیاز به کلید API، بدون هزینه به ازای هر درخواست، و بدون ریسک از‌کارافتادن پروژه به‌خاطر تغییر قیمت‌گذاری یا دسترسی. این یک تصمیم آگاهانه در برابر استفاده از یک API پولی بود؛ معماری RAG مستقل از ارائه‌دهنده است، پس جایگزینی با یک مدل پولی قوی‌تر در آینده، تغییری ساده خواهد بود.
- **اولویت‌بندی قانون‌محور است، نه پیش‌بینی‌شده با ML:** چون دیتاست هیچ برچسب واقعی اولویتی ندارد، این لایه یک جدول قانون بیزینسی صریح و قابل‌بازبینی است، نه یک مدل آموزش‌دیده (و غیرقابل‌اثبات).
- **SQLite به‌جای PostgreSQL:** برای اینکه پروژه در هر جایی بدون هیچ تنظیم دیتابیسی اجرا شود؛ کد از SQLAlchemy استاندارد استفاده می‌کند، پس مهاجرت به PostgreSQL فقط با تغییر یک خط رشته‌ی اتصال ممکن است.

## محدودیت‌های شناخته‌شده

- مدل کوچک و محلی تولید پاسخ، گاهی عبارات کلی یا کمی تکراری تولید می‌کند، و پاسخ‌ها ممکن است در صورت عبور از سقف تعیین‌شده‌ی توکن، ناتمام قطع شوند.
- سیگنال تشدید اولویت مبتنی بر `flags` (زبان توهین‌آمیز/نفی) فقط در داده‌ی تاریخی/آموزشی وجود دارد — تیکت‌های زنده این فیلد را ندارند، پس این منطق فعلاً فقط روی دیتاست تاریخی از‌پیش‌بارگذاری‌شده اعمال می‌شود، نه تیکت‌های جدید ثبت‌شده از طریق داشبورد.
- دیتابیس SQLite داخل کانتینر Docker بین ری‌استارت‌های کانتینر پایدار نیست — برای یک دمو مشکلی ندارد، ولی برای production واقعی مناسب نیست.
